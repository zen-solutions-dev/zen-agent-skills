- [x] (2026-09-01) Closed [`bug-0064`](../../.tasks/done/bug-0064-a-resubscribe-leaves-the-live-watcher-stopped-with-a-listener-attached.md): **reloading the observatory page permanently killed its live updates.** `LiveWatcher.unsubscribe` set the stop event, and `subscribe` decided the restart on `Thread.is_alive()` while clearing that event only on the branch that started a thread, so a subscribe arriving before the old thread had been scheduled to exit took the no-restart branch, left the request standing, and the surviving thread honoured it. Closing a report and opening another produces exactly that pair. **Not a narrow race, which the numbers are the point of**: setting the event wakes the thread, but the caller holds the interpreter and returns from `unsubscribe` into `subscribe` first, so it reproduced at 4000 of 4000 trials and at 0 of 4000 after the fix, and an end-to-end check went from no event in 10 seconds to a `change` event. The page went on rendering its live indicator over a report that had stopped following the corpus, which is indistinguishable from an idle corpus and is the failure class `SECURITY.md` names as a safety problem rather than a bug. The restart now turns on `_running`, state this class sets, decided in `_keep_running()` in one critical section with its reset, so a `subscribe` holding the lock can never observe a thread that has already decided to leave; the listener list is the authority and the stop event is demoted to the wake-up, which is what the class docstring already promised. **The handover was measured rather than argued**: two thread objects can briefly overlap, and an instrumented run over 4000 trials found at most one thread inside `poll_once` per watcher, so the old thread is finishing its exit rather than polling. The pre-existing lifecycle test passes unmodified, and it is why this went unseen: it joins the thread before asserting, which is exactly the wait that hid the defect. **One hazard the fix introduced was closed in the same change and is disclosed rather than left to be found**: deciding on `_running` means a `Thread.start()` that raises would leave the flag claiming a thread, where the old code's `is_alive()` would have let the next subscribe retry, so the failure now unwinds both the flag and the listener it was appended for. Its test kills the mutant that drops the unwind. 1113 tests to 1116.
